# 이슈 분류 (Triage)

프로젝트 이슈 트래커의 이슈들을 분류 역할 상태 머신에 따라 체계적으로 이동시킵니다.

저장소 설정에서 외부 PR을 요청 표면으로 취급하는 경우 PR도 함께 다룹니다: **PR은 코드가 첨부된 이슈**로 취급되며 동일한 역할과 상태 머신을 사용합니다.

분류 도중 이슈 트래커에 작성되는 모든 댓글이나 이슈 본문은 반드시 다음 안내 문구로 시작해야 합니다:

```
> *이 내용은 이슈 분류(Triage) 과정에서 AI에 의해 생성되었습니다.*
```

## 참고 문서

- [AGENT-BRIEF.md](AGENT-BRIEF.md): 에이전트용 브리프 작성법
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): `.out-of-scope/` 지식 베이스 운영법

## 분류 역할 (Roles)

2가지 **카테고리(Category)** 역할:
- `bug`: 무언가 고장남
- `enhancement`: 새로운 기능 또는 개선

5가지 **상태(State)** 역할:
- `needs-triage`: 메인테이너의 평가 필요
- `needs-info`: 제보자의 추가 정보 회신 대기
- `ready-for-agent`: 스펙 정의 완료, 에이전트 단독 작업 준비 완료
- `ready-for-human`: 사람 개발자의 직접 구현 필요
- `wontfix`: 처리하지 않기로 결정됨

PR의 경우: `ready-for-agent`는 브리프가 첨부되어 에이전트가 diff에 대한 후속 작업을 진행할 준비가 됨을 뜻하며, `ready-for-human`은 사람이 머지할 준비가 됨을 의미합니다.

모든 분류된 이슈는 정확히 하나의 카테고리 역할과 하나의 상태 역할을 가져야 합니다.

## 실행 방식

메인테이너가 `/triage`를 호출하고 자연어로 원하는 작업을 설명합니다. 예시:
- "내 확인이 필요한 이슈들을 보여줘"
- "#42번 이슈를 살펴보자"
- "#42번을 ready-for-agent로 변경해줘"
- "에이전트가 가져갈 수 있는 준비된 이슈가 뭐야?"

## 주의가 필요한 항목 표시

이슈 트래커를 조회하여 오래된 순서대로 3가지 버킷을 제시합니다:

1. **라벨 없음 (Unlabeled)**: 분류된 적 없음.
2. **`needs-triage`**: 평가 진행 중.
3. **`needs-info` 중 마지막 분류 메모 이후 제보자의 새 활동이 있는 항목**: 재평가 필요.

PR이 범위에 포함된 경우 외부 PR을 이 버킷에 포함하고 각 줄에 `[PR]` 또는 `[issue]` 태그를 붙입니다. 탐색 시에는 *외부* PR만 노출됩니다(트래커 설정에 외부 기여자의 기준이 정의됨). 따라서 협업자의 진행 중인 PR은 분류 작업 대상이 아닙니다. 이 필터는 탐색 시에만 적용되며, 명시적으로 지정된 PR은 작성자와 무관하게 항상 분류 대상이 됩니다.

각 항목별 건수와 한 줄 요약을 보여주고 메인테이너가 선택하도록 합니다.

## 특정 이슈 또는 PR 분류 단계

1. **컨텍스트 수집.** 이슈 또는 PR 전체(본문, 댓글, 라벨, 작성자, 날짜, PR의 경우 diff 포함)를 읽습니다. 이미 해결된 질문을 다시 묻지 않도록 이전 분류 메모를 파악합니다. 프로젝트 도메인 용어집을 사용하여 코드베이스를 탐색하고 해당 영역의 ADR을 준수합니다. 코드베이스에 대해 두 가지 검사를 실행합니다: (a) **중복성(redundancy)**: 요청 문구뿐만 아니라 도메인 개념을 기준으로 요청된 동작이 이미 구현되어 있는지 검색하고 확인한 위치를 보고합니다. 이미 구현되어 있다면 이미 구현된 `wontfix`가 됩니다(5단계). (b) **과거 기각 이력(prior rejection)**: `.out-of-scope/*.md`를 읽고 이번 요청과 유사한 내용이 있는지 확인합니다.

2. **추천안 제시.** 메인테이너에게 근거와 함께 카테고리 및 상태 추천안을 제시하고, 요청과 관련된 간략한 코드베이스 요약(이미 구현되어 있는지 여부 포함)을 덧붙입니다. 지시를 기다립니다.

3. **주장 검증.** 심문을 진행하기 전에 주장이 타당한지 검증합니다. 버그의 경우 제보자의 단계에 따라 재현합니다. PR의 경우 diff가 주장하는 대로 동작하는지 확인합니다: 체크아웃하고 관련 테스트나 명령어를 실행합니다. 어떤 결과가 나왔는지 보고합니다: 확인됨(코드 경로 포함), 실패함, 또는 세부 정보 부족(`needs-info`의 강력한 신호). 검증이 확인되면 훨씬 강력한 에이전트 브리프를 작성할 수 있습니다.

4. **심문 (필요 시).** 요청을 구체화해야 하는 경우 Skill 도구를 "grilling"과 "domain-modeling"으로 각각 호출하고, 한 번에 한 라운드씩 질문을 던져 요구사항을 구체화하며, 결정이 내려지는 즉시 도메인 용어를 정교화하고 `GLOSSARY.md`/ADR을 업데이트합니다.

5. **결과 적용:**
   - `ready-for-agent`: 에이전트 브리프 댓글을 게시합니다 ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: 에이전트 브리프와 동일한 구조로 작성하되 위임할 수 없는 이유(판단 필요, 외부 접근 권한, 설계 결정, 수동 테스트 등)를 명시합니다.
   - `needs-info`: 분류 메모를 게시합니다 (아래 템플릿 참조).
   - `wontfix`: 이슈를 닫으며, *이유*에 따라 다음과 같이 댓글을 작성합니다:
     - **이미 구현됨**: 해당 변경사항이 코드베이스에 이미 존재함. 위치를 안내하되, `.out-of-scope/`에는 작성하지 **마세요** (해당 지식 저장소는 구현된 기능이 아니라 *기각된* 요청을 위한 것입니다).
     - **기각됨 (버그)**: 정중한 설명을 남기고 닫습니다.
     - **기각됨 (개선 제안)**: `.out-of-scope/`에 기록하고 댓글에서 링크한 뒤 닫습니다 ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: 해당 역할을 적용합니다. 부분적인 진행 상황이 있다면 선택적으로 댓글을 남깁니다.

## 빠른 상태 재정의 (Quick state override)

메인테이너가 "#42를 ready-for-agent로 변경해줘"라고 지시하면 이를 신뢰하고 역할을 직접 적용합니다. 수행할 작업(역할 변경, 댓글, 닫기 등)을 확인한 뒤 실행하세요. 심문은 건너뜁니다. 심문 세션 없이 `ready-for-agent`로 변경하는 경우 에이전트 브리프를 작성할지 메인테이너에게 질문하세요.
