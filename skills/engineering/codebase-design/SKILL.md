# 코드베이스 설계 (Codebase Design)

**깊은 모듈(Deep module)** 을 설계하세요: 작은 인터페이스 뒤에 풍부한 동작을 담고, 깔끔한 경계선(Seam)에 배치하며, 그 인터페이스를 통해 테스트할 수 있도록 만듭니다. 코드를 설계하거나 구조를 개편할 때 이 언어와 원칙들을 사용하세요. 목표는 호출자에게는 **레버리지(Leverage)** 를, 유지보수자에게는 **응집성(Locality)** 을, 모두에게는 **테스트 용이성**을 제공하는 것입니다.

## 용어집 (Glossary)

이 용어들을 정확히 사용하세요. "컴포넌트", "서비스", "API", "경계(Boundary)" 등으로 임의 대체하지 마세요. 일관된 어휘가 핵심입니다.

**모듈 (Module)**:
인터페이스와 구현을 갖춘 모든 것. 규모와 무관하게 적용됩니다: 단일 함수, 클래스, 패키지, 또는 계층을 가로지르는 슬라이스.
_지양할 표현_: 유닛, 컴포넌트, 서비스

**인터페이스 (Interface)**:
호출자가 모듈을 올바르게 사용하기 위해 알아야 하는 모든 것: 타입 시그니처뿐만 아니라 불변식(Invariant), 호출 순서 제약, 오류 모드, 필수 설정, 성능 특성까지 포함합니다.
_지양할 표현_: API, 시그니처 (타입 수준의 표면만을 가리키므로 너무 좁은 의미임)

**구현 (Implementation)**:
모듈의 내부에 있는 실제 코드 본체. **어댑터**와 구분됩니다: 작은 어댑터 뒤에 방대한 구현이 있을 수도 있고(Postgres 리포지토리), 큰 어댑터 뒤에 사소한 구현이 있을 수도 있습니다(인메모리 페이크). 경계선이 주제일 때는 "어댑터"를 쓰고, 그 외에는 "구현"을 쓰세요.

**깊이 (Depth)**:
인터페이스에서의 레버리지. 호출자(또는 테스트)가 학습해야 하는 인터페이스 단위당 실행할 수 있는 동작의 양. 작은 인터페이스 뒤에 방대한 동작이 숨겨져 있을 때 **깊은 모듈(Deep module)** 이라 하고, 인터페이스가 구현만큼이나 복잡할 때 **얕은 모듈(Shallow module)** 이라고 합니다.

**경계선 (Seam)** _(마이클 페더스, Michael Feathers)_:
그 자리를 직접 수정하지 않고도 동작을 변경할 수 있는 위치; 모듈의 인터페이스가 위치하는 *장소*. 경계선을 어디에 둘 것인가는 그 뒤에 무엇을 넣을 것인가와는 별개의 독립적인 설계 결정입니다.
_지양할 표현_: Boundary (DDD의 Bounded context와 혼동됨)

**어댑터 (Adapter)**:
경계선에서 인터페이스를 충족시키는 구체적인 구현체. 내부 내용이 아니라 *역할*(어떤 슬롯을 채우는가)을 나타냅니다.

**레버리지 (Leverage)**:
호출자가 깊은 모듈로부터 얻는 혜택. 적은 인터페이스를 배우고도 더 많은 기능을 활용할 수 있습니다. 단 하나의 구현이 N개의 호출 위치와 M개의 테스트에서 가치를 회수합니다.

**응집성 (Locality)**:
유지보수자가 깊은 모듈로부터 얻는 혜택. 변경사항, 버그, 지식, 검증이 호출자 전체로 흩어지지 않고 한곳에 집중됩니다. 한 번 고치면 모든 곳에서 고쳐집니다.

## 깊은 모듈 vs 얕은 모듈

**깊은 모듈 (Deep module)** = 작은 인터페이스 + 방대한 구현:

```
┌─────────────────────┐
│   작은 인터페이스   │  ← 적은 메서드 수, 단순한 매개변수
├─────────────────────┤
│                     │
│    깊은 구현체      │  ← 복잡한 비즈니스 로직 은닉
│                     │
└─────────────────────┘
```

**얕은 모듈 (Shallow module)** = 큰 인터페이스 + 빈약한 구현 (피해야 함):

```
┌─────────────────────────────────┐
│        큰 인터페이스            │  ← 많은 메서드, 복잡한 매개변수
├─────────────────────────────────┤
│    단순 통과형 구현체           │  ← 단순히 다음으로 위임만 함
└─────────────────────────────────┘
```

인터페이스를 설계할 때 스스로에게 질문하세요:
- 메서드 수를 줄일 수 있는가?
- 매개변수를 단순화할 수 있는가?
- 더 많은 복잡성을 내부에 숨길 수 있는가?

## 핵심 원칙

- **깊이는 구현이 아닌 인터페이스의 속성입니다.** 깊은 모듈은 내부적으로 모킹 가능하고 교체 가능한 작은 부품들로 구성될 수 있습니다. 단지 그것들이 외부 인터페이스에 노출되지 않을 뿐입니다. 모듈은 외부 인터페이스의 **외부 경계선(External seam)** 뿐만 아니라 내부 구현 전용의 **내부 경계선(Internal seam)** 을 가질 수 있습니다.
- **삭제 테스트 (Deletion test).** 이 모듈을 삭제한다고 상상해 보세요. 복잡성이 사라진다면 그것은 단순 패스스루 모듈이었습니다. 반대로 복잡성이 N개의 호출자 곳곳으로 흩어져 다시 나타난다면, 그 모듈은 제 역할을 훌륭히 해내고 있던 것입니다.
- **인터페이스가 곧 테스트 표면입니다.** 호출자와 테스트는 동일한 경계선을 가로지릅니다. 만약 인터페이스를 *건너뛰어* 내부를 테스트하고 싶다면, 모듈의 형태가 잘못되었을 가능성이 높습니다.
- **어댑터가 1개면 가상의 경계선, 2개면 진짜 경계선입니다.** 경계선을 가로질러 실제로 달라지는 것이 없다면 굳이 경계선을 도입하지 마세요.

## 테스트 가능성을 위한 설계

좋은 인터페이스는 테스트를 자연스럽게 만듭니다:

1. **의존성을 직접 생성하지 말고 주입받으세요.**

   ```typescript
   // 테스트 용이함
   function processOrder(order, paymentGateway) {}

   // 테스트 어려움
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **부수 효과(Side effect)를 일으키지 말고 결과를 반환하세요.**

   ```typescript
   // 테스트 용이함
   function calculateDiscount(cart): Discount {}

   // 테스트 어려움
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **표면적을 작게 유지하세요.** 메서드가 적을수록 필요한 테스트도 적어집니다. 매개변수가 단순할수록 테스트 설정이 간단해집니다.

## 관계

- 하나의 **모듈**은 정확히 하나의 **인터페이스**를 가집니다 (호출자와 테스트에 노출하는 표면).
- **깊이**는 **모듈**의 속성이며, **인터페이스**와 대비하여 측정됩니다.
- **경계선(Seam)** 은 모듈의 **인터페이스**가 존재하는 위치입니다.
- **어댑터**는 **경계선**에 위치하여 **인터페이스**를 만족시킵니다.
- **깊이**는 호출자에게 **레버리지**를, 유지보수자에게 **응집성**을 제공합니다.
